# 面试深挖准备清单

涵盖RAG知识库项目的两个核心深挖方向：**文档解析与分块策略**、**检索增强策略**。

---

## 方向一：文档解析与分块策略

### Q1: 项目支持哪些文档格式？如何处理不同格式？

**准备要点**:
- 使用LOADER_DICT工厂模式，文件扩展名映射到加载器函数
- PDF: PyMuPDF逐页提取文本，每页生成独立Document；低文本页面（<50字符）预留OCR回退
- DOCX: python-docx提取段落文本
- PPTX: python-pptx提取幻灯片文本，用`[Slide N]`标记
- 图片: RapidOCR（基于ONNX Runtime，比PaddleOCR更轻量）
- 纯文本: UTF-8直接读取
- 扩展只需在LOADER_DICT注册新加载器

### Q2: 为什么选择ChineseRecursiveTextSplitter？chunk_size=250的依据是什么？

**准备要点**:
- 中文分隔符优先级：`\n\n → \n → 。→ ！→ ？→ ，→ " " → ""`
- 保证在自然语义边界（句号、问号、感叹号）处分块
- 250字符：中文信息密度高（1个中文=3-4个英文token），250字符≈750 tokens，是嵌入模型的输入上限；较小chunk提高检索精度减少噪声
- overlap=50：保证跨chunk的语义连续性，防止关键信息在chunk边界处断裂
- 与英文典型512 tokens的chunk相比，中文250更合理

### Q3: zh_title_enhance解决了什么问题？

**准备要点**:
- 独立chunk丢失文档层级上下文（不知道来自哪个章节）
- 通过预置`[章节标题] > [小节标题] > chunk内容`的路径信息
- 检索结果携带层级导航信息，用户和LLM都能理解chunk所处位置
- 特别适合技术文档、产品手册等有明确标题层级的内容

### Q4: 如果文档是扫描件，如何处理？

**准备要点**:
- PDF先用PyMuPDF尝试文本提取（非扫描页）
- 低文本页面（<50字符）判定为扫描页，回退OCR
- RapidOCR中文识别效果好，ONNX Runtime推理部署方便
- RapidOCR vs Tesseract: 中文OCR准确率更高，不需要额外语言包
- 图像预处理（去噪、增强对比度）可进一步提升OCR质量

### Q5: 是否有更好的分块策略？语义分块怎么实现？

**准备要点**（可扩展方向）:
- 固定大小分块的局限：可能切断语义完整单元
- 语义分块：将文本拆为句子，计算相邻句子的embedding余弦相似度
- 在"相似度低谷"处（相似度突然下降）设置分块边界
- 优点：每个chunk是自然的语义单元；缺点：计算量大，需LLM辅助确定阈值

## 方向二：检索增强策略

### Q6: 为什么需要混合检索？BM25和FAISS各自擅长什么？

**准备要点**:
- BM25（关键词匹配，Sparse Retrieval）：
  - 擅长精确匹配：专业术语、编号、代码、人名
  - 基于TF-IDF，有明确的词频统计意义
  - 盲区：同义词、改写、跨语言（"电脑" vs "计算机"）
- FAISS（语义检索，Dense Retrieval）：
  - 擅长语义匹配：同义词、概念关联、模糊查询
  - 通过embedding捕捉深层语义
  - 盲区：专有名词精确匹配弱、数值查询不准
- 互补覆盖：两者结合召回率大幅提升

### Q7: RRF融合相比简单的分数归一化有什么优势？

**准备要点**:
- RRF = Reciprocal Rank Fusion
- 公式：`score(d) = Σ w_i / (k + rank_i)`
- 尺度不变性（scale-invariant）：基于排名而非原始分数
- BM25和FAISS的分数量纲完全不同（tf-idf vs cosine similarity），直接归一化容易失真
- RRF天然消除量纲差异
- k=60：控制排名区分度。k越大，高低排名差异越小；k越小，高排名优势越明显但噪声风险增加
- 60是业界经验值（源自多数据集实验）

### Q8: CrossEncoder和Bi-encoder的区别是什么？为什么先粗排再精排？

**准备要点**:
- Bi-encoder (FAISS)：
  - Query和Document分别独立编码为向量
  - 向量是固定的，支持预建索引
  - 检索速度O(n) → 可以处理百万级数据
  - 交互浅：query和doc的编码过程互不相见
- CrossEncoder (Reranker)：
  - 将(query, document)拼接，联合编码
  - BERT全注意力机制使query和doc深度交互
  - 精度显著更高（同一模型CrossEncoder > Bi-encoder）
  - 速度O(n*candidates)：每个候选对都需过BERT，速度慢
- 两级策略：粗排(Bi-encoder top-10) → 精排(CrossEncoder top-3)
- 默认模型：`BAAI/bge-reranker-large`（BGE系列，中文重排序SOTA）

### Q9: score_threshold=0.35是怎么确定的？调整它有什么影响？

**准备要点**:
- 经验值，平衡精度和召回
- 越低（如0.0）：召回更多但噪声也多 → 适合探索性搜索
- 越高（如0.7）：只返回高置信度结果 → 适合事实性查询
- 0.35偏向"宁可漏检也不误检"，适合知识库场景（用户期望准确答案）
- 实际可通过用户反馈数据动态调整

### Q10: 如果检索结果都不好怎么办？

**准备要点**:
- 多层兜底策略：
  1. 放宽score_threshold重试
  2. 纯BM25回退（如果语义检索漂移）
  3. LLM诚实告知"未找到相关信息"
- Prompt中已写明："如果参考资料中没有相关信息，请如实告知"
- 这是RAG系统的诚实性设计—宁可说不知道也不编造

### Q11: 如何提高检索质量？（可扩展方向）

**准备要点**（展示深度思考能力）:

1. **查询改写 (Query Rewriting)**:
   - LLM改写用户query：消除歧义、纠正口语化、补充上下文
   - 生成多个改写版本，多路检索取并集
   - 效果：提升15-30%的检索准确率

2. **HyDE (Hypothetical Document Embeddings)**:
   - LLM先生成一个"假设答案"
   - 用假设答案的embedding检索
   - 假设答案与真实答案在语义空间更接近
   - 对开放域问答、解释性问题特别有效

3. **多路召回**:
   - 当前2路(BM25+FAISS) → 扩展到3+路
   - 增加：知识图谱检索、网页搜索、关键词全文倒排
   - 学习融合权重（LambdaMART等LTR模型）替代固定RRF权重

4. **Query2Doc / 伪相关反馈**:
   - 用初次检索的top结果作为正例
   - 提取关键词扩展原始query
   - 二次检索精度更高

### Q12: BM25索引为什么每次重启需要重建？

**准备要点**:
- 当前实现：BM25索引在内存中，从KBService获取所有文档文本后构建
- 这是有意为之的简化，确保BM25索引与FAISS数据一致
- 如果要持久化：可用pickle序列化corpus和IDF统计
- 对于求职项目的规模（数千文档），每次冷启动重建耗时<1秒

### Q13: 为什么使用OpenAI API而不是本地部署嵌入模型？

**准备要点**:
- text-embedding-3-small: 1536维，中文排名前列，价格$0.02/1M tokens
- API方式：免去GPU部署成本、模型更新无需维护、易于切换其他API提供商
- 本地部署备选：BGE-M3（BAAI开源，1024维），需要GPU ~2GB显存
- API密钥通过环境变量注入，容器化部署时安全隔离
- OpenAI兼容协议 → 可无缝切换到国产API（百度千帆、阿里百炼等）

### Q14: FAISS vs Milvus vs Chroma怎么选择？

**准备要点**:
- FAISS（当前使用）:
  - 优势：轻量（pip install即可），单机百万级延迟<10ms，零运维
  - 劣势：不支持分布式，需手动持久化
  - 适用：求职项目、PoC、单机场景
- Milvus:
  - 优势：分布式、支持10亿+向量、混合查询、数据持久化
  - 劣势：部署复杂（需etcd+MinIO+Pulsar）
  - 适用：生产环境、大数据量
- Chroma:
  - 优势：开发者友好、内置embedding、自动持久化
  - 劣势：性能弱于FAISS和Milvus
  - 适用：快速原型
- KBServiceFactory模式保证了向量库切换只需改配置和注册新实现

### Q15: 整个系统最可能出问题的环节是什么？

**准备要点**（展示系统思维）:
1. **gRPC通信超时**: 文件大（>50MB）时嵌入耗时长，需设置合理的deadline（当前100MB上限）
2. **嵌入API限流**: OpenAI有速率限制，批量文档需控制并发（当前串行处理）
3. **FAISS内存溢出**: chunk_size×chunk数量 > 可用内存会OOM（预留7GB）
4. **MinIO网络延迟**: 文件转存时网络抖动影响上传，Java端已有重试机制
5. **跨语言序列化**: gRPC Proto版本不一致导致解析失败，通过共用proto目录保证
